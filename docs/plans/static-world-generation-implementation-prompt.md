## Ownership and runtime products

Put game schemas, file loading, reference resolution, material semantics and content identity in a new `game.colony.content` module under `game/colony/`. Keep game orchestration and the public game generator in `game.colony.worldgen`. Put numeric procedural primitives and compiled generation execution in the existing `engine.sim:worldgen` area. Add a small partition only where there is a distinct responsibility; follow registration and umbrella rules.

The engine receives validated, owned numeric descriptions: IDs, scalar parameters, bounds, weights and enumerated operation kinds. It never reads content files, environment variables, services or game modules. It has no knowledge of oxygen, sandstone, a frozen biome or a starting rocket. The game compiles names and references once into those descriptions.

Use these conceptual ownership boundaries; adapt names to repository conventions:

- `ContentCatalog`: immutable, owned material/biome/template/profile definitions and compiled lookups. A world session owns it. No global registry, mutable singleton, raw TOML node or reference to parse scratch survives loading.
- `GenerationPlan`: owned engine-side numeric recipe compiled from one profile and catalog. Its rule identities and random-stream keys remain stable across file/table ordering.
- `GeneratedWorld`: owns the terrain `ChunkGrid`, immutable generation metadata, start/spawn markers, initial mobile-matter regions, and a bounded generation report. Return `Expected<GeneratedWorld>`; never mutate the live grid while generating.
- `WorldDescriptor`: pack schema version, generator algorithm version, profile ID, seed, canonical content fingerprint and world-unit convention. This is the identity needed to reproduce the baseline, not just the seed.

Use the following coordinate contract throughout generation, physics, presentation, tools and actors:

- World positions, Box2D body geometry, camera distances, velocities and accelerations use metres, metres/second and metres/second squared. One fine cell has edge `h = 1/3 m`. Keep normal gravity at its existing metre-based value; do not multiply gravity by three.
- Fine cell `(i,j)` has nominal bounds `[i*h,(i+1)*h) × [j*h,(j+1)*h)` and centre `((i+0.5)*h,(j+0.5)*h)`. Metres to fine cells uses checked `floor(position*3)`, never truncation or unsigned conversion before validation. Use +Y up. Normalized depth increases from the world top downward.
- Construction tile `(tx,ty)` starts at fine cell `(3*tx,3*ty)` and covers exactly 3 by 3 cells. Multi-tile footprints are integer multiples of three on a globally anchored lattice at `(0,0)`. Chunk edges need not align with construction tiles: 128 is not divisible by three. Validate and dirty every touched chunk for cross-chunk placement; reject any footprint outside the world. The final one-cell remainder at the top/right cannot hold another complete tile and belongs to the protected boundary.
- Keep chunk indexing and path waypoints in integer fine-cell coordinates. Convert explicitly at actor, collider, camera, picking and shader boundaries. Audit spawn sizes, waypoint tolerances, wake radii, tool reach, ladder geometry, camera framing and collider-neighbour discovery; existing casts from `BodyState` positions to chunk coordinates are no longer valid.
- Put the game scale and checked conversion helpers in one small game-owned module used by its adapters. Pass numeric cell size/origin into generic app/physics consumers; those layers must not import game or acquire a second hard-coded 3:1 scale. Snapshot body states are metres. Persist the integer ratio `cells_per_metre = 3`, construction tile size and reference thickness in `WorldDescriptor` and checkpoint identity.
- Use one metre of reference thickness. A nominal fine-cell volume is `1/9 m3`; nine fine cells occupy `1 m3`. Initial-matter estimates integrate the empty fraction of the reconstructed terrain polygon inside each span cell, rather than counting its whole nominal volume if a neighbouring contour intrudes. This is a geometric initial-mass estimate, not an equilibrium fluid model. Use the same contour geometry for clipping the preview and computing this fraction. The future MPM grid spacing and particles per metre are independent solver decisions; do not equate them with this persistent terrain lattice.

Author physical frequencies, distances, radii, widths and texture periods in metres, including field names with unit suffixes. Specify discrete template extents/offsets explicitly as fine-cell integers and construction footprints as tile integers. Reject nonrepresentable discrete dimensions instead of silently rounding author intent. Sample fields at global cell centres converted to metres.

Keep three outputs distinct:

1. **Static terrain:** bonded solids such as rock, ore, ice and masonry. Only these IDs may occupy `ChunkGrid`; zero means absence of static terrain. A zero cell does not prove physical vacuum or a breathable atmosphere.
2. **Generation metadata:** region ownership and biome ID, feature instances, protected starting area and start marker. Retain compact region/site descriptions; do not add biome strings or large records to every `Cell`.
3. **Initial mobile matter:** unsimulated initial conditions for future particles, stored as bounded region records with canonical horizontal spans over empty terrain. Each record contains material ID, temperature in K, bulk density in kg/m3 and stable region identity. Derive volume and mass from spans and the world-unit convention. No particles or solver state exist yet.

Use at most one initial mobile-matter assignment per occupied span cell in this milestone. This is an initialization-format limitation, not a future single-species-per-cell solver contract. Author liquid/granular fill height as an integer fine-cell boundary, converted to metres for geometric clipping; reject off-lattice heights. Resolve explicit fill precedence before emitting disjoint spans; gas fills only remaining unassigned empty cells. Never double count liquid and gas or granular material. Empty unassigned volume contains no initialized matter. Initial regions are a baseline preview, never live atmosphere state after terrain edits; label the overlay accordingly and hide it once edits invalidate its geometry, until regeneration.

Do not add speculative PB-MPM constitutive models, yield/friction parameters, particle resolution settings or phase-transition tables. The current catalog distinguishes material phase from its representation, so solid snow can be particle matter while solid ice is terrain. Material physical constants beyond those consumed by initialization/inspection wait for their owning simulator.

## Content format and validation

Use a single versioned TOML pack under `assets/worldgen/default/`:

- `pack.toml`: schema version, pack identity and explicit relative file entries.
- `materials.toml`: named material records.
- `biomes.toml`: named biome recipes with nested named composition/deposit entries.
- `fields.toml`: named noise descriptors.
- `features.toml`: named templates made from ordered rectangle/ellipse/capsule paint or carve operations, attachment markers and reservation bounds.
- `worlds.toml`: named world profiles, ordered placement/generation rules and start guarantees.

Use keyed tables, not arrays, delimiter-packed strings or a second parser. Example forms are `[materials.sandstone]`, `[biomes.temperate.deposits.copper]`, `[worlds.frontier.rules.ore_copper]` and `[features.landing.operations.floor]`. This fits the existing codec. Collection record names must match `[a-z][a-z0-9_]*`; references are strings. Reject dotted or otherwise ambiguous record names. Preserve fully qualified keys and original source locations when reporting errors.

Build a small game-owned document grouper: classify known collection prefixes, identify record keys, strip only the known prefix for a typed record schema, then call the existing `config::resolve` and cross-field validation. Do not add another conversion/constraint system. Validate unknown fields, required fields and reference integrity explicitly. Required content values must not silently inherit C++ defaults. Use defaults only for documented optional algorithm controls. Content records are file/programmatic inputs; CLI/environment select the pack/profile/seed rather than overriding arbitrary catalog members.

Keep `engine.core`'s scalar configuration contract unchanged unless a demonstrated codec defect prevents this format. Do not extend it with recursive values or arrays just to imitate ONI YAML. No inheritance, include recursion, mod override stacks, script execution or automatic file watching in this milestone. The pack manifest is the complete file set; validate relative paths and reject traversal outside its root. Sort records canonically rather than depending on directory iteration.

|---|---|

Biomes reference terrain materials, fields, temperature base/variation, weighted composition and deposit rules. Each biome also has a display name and `preview_color_rgba` for inspection. A biome is a spatial recipe, never a material. Ruins and vents are feature types, never terrain IDs. World profiles choose a default building material by reference for the existing build fixture. Give masonry a one-metre texture period so its pattern stays aligned to the global construction lattice across chunks. Required physics/game flags must not be inferred from display names.

Physical identity and visual mapping are distinct. Each cell carries its authoritative material ID and temperature; the material ID resolves a visual record. Derive UV on the GPU as `world_position_m.xy / texture_period_m`; the effective W is the resolved bindless texture slot, not a stored third float coordinate. Do not grow `sim::Cell` with UVW, texture handles or draw data, or allocate a full-world UV sidecar. This milestone needs one world-anchored mapping per material, not per-cell rotation/UV overrides. Moving fractured bodies can acquire body-local mapping in the later destruction milestone.

Use positive finite values and checked arithmetic for frequencies, scales, densities and dimensions. Check weights, totals, thresholds, reference kinds, bounds, supported versions, unique numeric IDs, stable rule IDs, duplicate order values, legal operation fields, candidate/work limits and output-size limits before allocation or scheduling. Reject unsupported algorithm names. Diagnostics must identify the file, record, field and offending reference. Keep explicit validation errors distinguishable from cancellation, I/O failure and exhausted placement constraints.

## Procedural algorithm decisions

Use a finite typed operation library, not an expression language, plugin registry, visual graph editor or arbitrary scripting system. Authors compose named fields, biome references, masks and ordered passes. Adding content requires data edits; adding an entirely new algorithm legitimately requires code.

Use FastNoiseLite behind one private C++ implementation boundary for OpenSimplex2, Perlin, cellular distance fields, fBm, ridged fractals and domain warp. Pin an immutable upstream version/commit in the repository's dependency mechanism and record the license. Resolve and record the pin during implementation; do not consume a moving branch. Existing splitmix-style hashing remains useful for discrete selections and stream derivation. The existing local lattice-noise helper does not provide this full operation set; do not grow a competing handwritten noise library. No FastNoiseLite types may escape exported PPR interfaces.

Expose only the operations needed by the shipped profiles:

| Operation | Exact role |
|---|---|
| Poisson disk site placement | Macro regions and feature candidates with configured minimum separation and a bounded attempt count. Include a fixed start site before placing others. |
| Voronoi region ownership | Nearest site in optionally warped world coordinates, squared Euclidean distance, lowest stable site ID on ties. Use a spatial index with a correct nearest-distance stopping condition; do not scan every site for every cell. |
| Biome assignment | First reserve required biome counts among eligible sites, then weighted selection among eligible biomes. Eligibility uses normalized depth and distance from start. Process constraints most-restricted-first with stable ID ties; infeasibility is an explicit error. No PowerTree or weighted-area guarantee is claimed. |
| Noise and domain warp | Coherent interior variation, irregular boundaries, cave masks and deposits. Warp sample coordinates, not cell storage or collider coordinates. Each field has its own stable stream key. |
| Layered composition | Ordered depth bands and cumulative weighted material intervals from a coherent field. Do not independently choose a random material for every cell. Later deposit rules only replace eligible host materials. |
| Threshold caves | Carve where a named field lies in an explicit interval, clipped by biome/depth masks and reservations. |
| Tunnel worms | Seeded bounded walks with the existing discrete heading approach, radius/length/turn controls and capsule/disc rasterization. Use for winding passages and elongated ore veins. |
| Room connection | Connect selected traversal room anchors with a deterministic minimum spanning tree; allow an explicit bounded number of extra links. Rasterize finite-width capsule segments. Sealed pockets are excluded. |
| Feature templates | Ordered terrain/carve primitives and markers with a bounding reservation, biome/depth eligibility, spacing and optional horizontal reflection. Reject overlaps with higher-priority reservations. No arbitrary entity-spawning system. |
| Initial matter fills | Bounded connected-component flood fill inside a reserved container. Verify connectivity/containment against reconstructed empty geometry, including diagonal saddle openings, rather than assuming a four-neighbour empty-cell flood proves sealing. For liquid/granular fills, clip to the authored horizontal fill height in metres; gas fills remaining eligible volume. Write canonical spans plus the fill height needed for exact preview/volume clipping. No fluid relaxation step. |

A chamber graph provides geometric connectivity only. It does not prove platformer reachability with jumps, ladders, actor clearance or gravity. The starting-area test below is deliberately stronger locally; global movement guarantees wait for the actual player controller.

Execute these phases:

1. Validate and compile the pack/profile, derive the world descriptor and named random streams.
2. Place macro sites, assign biomes and reserve the start region, permanent world boundary and required feature candidates. Derive all nonlocal decisions before chunk rasterization.
3. Fill terrain from biome host materials, layers and temperature fields; apply ore/lens/vein replacements in explicit order.
4. Carve cave fields, selected room connections and worms. Respect reservations and permanent boundary masks at every write.
5. Stamp the landing-area template, resource alcoves, sealed reservoir containers and optional ruin shells. Required features fail generation if they cannot be placed; optional omissions appear in the report.
6. Resolve initial mobile-matter fills against final terrain. Leave terrain empty at those positions and keep their mass only in the initialization records.
7. Validate final terrain, spawn clearance/support, protected bounds, local resource guarantees, reserved-pocket containment and all output references. Compute canonical summaries/checksums, then return the owned candidate.

The order above is part of the generator version. Rule order is explicit within a phase. Reject rules scheduled in incompatible phases. Do not “repair” results by randomly rerolling the world seed or painting arbitrary fallback resources after validation. The start template and its resource alcoves are an intentional data-authored guarantee. Bounded retries of a feature's candidates use only that feature's stream; exhaustion identifies the rule that failed.

The default profile must include a temperate starting region, a cold region, a mineral-rich region and a hot/deep region, with differences in composition, cave structure and temperature. Ship a second profile using the same code with visibly different cave density, region weighting and deposit geometry. Use original PPR names, palettes and templates. Start with at least twelve material definitions spanning terrain rock/ore/ice/masonry and particle water/gas/sand/snow/pebbles; particle records are demonstrably absent from terrain collision data. A vent feature may be an inert geometric marker now; do not claim it emits anything.

For the start guarantee, provide a reserved chamber with a supported spawn, at least three metres (nine fine cells) of vertical clearance and a continuous supported, level route to two resource alcoves. Configure room dimensions, materials, route widths, minimum adjacent diggable resource amounts and maximum distances in data; use physical area/volume or explicitly named fine-cell counts for resource minima. Validate against the actual actor body dimensions in metres and reconstructed collision surfaces, not a point-cell search. The camera and exactly one normal player spawn consume the generated start marker. Keep existing many-agent profiling fixtures as explicit test/profile behavior rather than scattering the normal start across arbitrary caves.

## Determinism and bounded execution

The reproducibility key is `(generator version, canonical content, profile, seed)`. Never seed from wall time, hardware RNG, scheduling order, container iteration or a shared mutable random engine.

Specify a fixed byte-level hash and fixed integer PRNG/seed derivation. Use the existing deterministic hash where suitable. Derive independent streams from the world seed plus stable field/rule IDs and feature/site ordinal. Use rejection sampling for unbiased bounded integer selection. Do not use `std::hash`, implementation-defined random distributions or native-struct byte dumps for persistent checksums. Content fingerprints use canonical resolved values, sorted keys, explicit lengths and little-endian numeric encoding, excluding comments, source paths and provenance. Algorithm/library upgrades that change results require a generator-version change.

Guarantee bit-identical output for the same build and inputs, independent of worker count, chunk visit order and table/file order. Do not promise cross-compiler or cross-platform floating-point equality. Hash integer material IDs and explicit floating bit patterns in a defined order; include metadata and initial matter spans, not just terrain.

Use the existing scheduler through an explicit execution boundary, following `concurrency-patterns` and the asynchronous lifecycle below. Parallelize chunk field evaluation/rasterization and other measured independent batches; keep ordered layout decisions and unsafe shared operations serial on the background coordinator. Retain a serial execution mode for tests and small workloads; it must still run off the UI thread in interactive use. Preallocate output slots and give workers exclusive chunk ownership; do not race lazy grid materialization or mutate container topology concurrently. Generate nonlocal features once, assign their raster operations to intersecting chunks in canonical order, and evaluate field samples in global coordinates so seams match.

No full-world float raster per noise field. Bound per-worker chunk scratch, sites, rules, templates, retry counts, spans, component searches and diagnostics. Use compact transient occupancy/visited bitsets where global topology requires them. Reject requests exceeding declared implementation limits with an error naming the limit; do not silently clamp content or truncate required output. Quantify bounds in the schema reference and distinguish implementation safety caps from content tuning.

Pass an explicit cancellation context. Check it between bounded work units and during long flood fills/walks. On cancellation or first failure, stop admission, drain admitted work on the background coordinator and discard the candidate there; the UI only observes completion. No task may borrow a destroyed plan, catalog, output or callback. Use error macros, preserve the first error during cleanup and report `operation_canceled` distinctly. Exceptions reaching an operational boundary must be translated or reported per `AGENTS.md`.

Record phase timings and peak generation scratch/allocation accounting through existing facilities. At 4096 squared there are 16,777,216 cells; on an ABI where `sizeof(Cell)==8`, one fully resident grid payload alone is 128 MiB. Confirm actual sizes and account for old plus candidate worlds during regeneration. Do not claim a speedup or invent a global performance budget. Measure fixed seeds on the same build/hardware and report raw timing/memory, including worst observed placement attempts and span counts.

## Asynchronous startup, progress and cancellation

Use one game-owned world-job state machine for initial generation, regenerate, reload-and-regenerate, and checkpoint preparation. Do not add a general background-task service. A job owns its immutable request, monotonic job ID, cancellation context, progress storage and eventual `Expected` result. Its candidate owns all catalog/grid/metadata/image bytes it needs. The UI owns only control state and observations, never the candidate's mutable storage. Separate the job ID from the committed world generation: a canceled or failed request must not publish a new world epoch.

**Startup order:** bootstrap the existing platform, window, input/player, renderer/render lane and UI; initialize only the content-independent resources needed to draw the loading screen and normal passes. Do not load the terrain pack, generate cells, construct world physics, or upload a world from `initialize()`. Enter the normal run loop with an explicit no-world state and an already-open “Generating terrain” modal. Render a lightweight background and that modal first. Only after observing the first successful loading-screen presentation through the normal asynchronous result path may a subsequent update admit the initial job. Queue submission/CPU consumption alone is not presentation evidence. If no existing result field records presentation success, add the narrow result flag; never wait synchronously for it. While minimized, keep the request queued until a drawable frame can be presented; still handle native events and close. Engine bootstrap errors before a usable UI retain the existing startup error path.

World-dependent tick, capture, inspector, tools, selection and camera-follow code must explicitly handle absence of a live session. Continue normal editor input/UI/render service in this state. After publication, frame the generated spawn and enable the controlled actor. Do not hide generation in a constructor, a lazy getter, the first update, a render callback or a future destructor.

**Execution:** reuse `ParallelScheduler` for one persistent game-owned, background-priority coordinator worker and inject a distinct existing background pool for chunk work at the application boundary. The coordinator owns sequential job orchestration and can wait for its admitted chunk group; it must not occupy the same pool whose child tasks it awaits. Resolve shared pool dependencies at the top level, not inside sim. Reuse these workers across reloads; do not create an OS thread per chunk or recreate a pool per world. Explicitly pass the intended pool to parallel helpers, and verify that their nested-worker serial fallback does not defeat fan-out. Bound outstanding jobs at one and bound admitted chunk batches. Queue-full handling may defer work or run a slice on the coordinator, never on the UI. Small/one-worker configurations must complete without deadlock or busy spinning.

UI admission uses a non-waiting queue policy and handles busy/full/closed/canceled distinctly. On full, retain the single pending request and retry on a later update; do not silently drop it or use `wait_if_full`. The worker pipeline owns content reads, parsing/reference validation, image decoding, generation, topology checks, initial-mass calculations, checksums, and CPU presentation preparation. Prepare the isolated candidate driver/physics there if its source-verified ownership and allocator contracts permit exclusive cross-thread transfer; otherwise split only the thread-affine preparation into bounded owner-lane steps. No live registry/scene is accessed by generation workers. Return owned results; never transport TLS scratch, parser views or non-owning callbacks into expired storage.

The UI consumes readiness with nonblocking polls; `future.get()` is allowed only after a ready check, and must only move owned results. It must not call `WaitGroup::wait`, scheduler join, blocking channel receive/flush, synchronous file/image load, GPU fence/idle wait or long destruction. A synchronous numeric generator remains useful behind this worker boundary and for CPU-only CLI/tests; those headless callers may wait and emit progress to logs without initializing a window.

**Visible states:** queued; loading/validating content; layout; terrain/composition; caves/features; initial matter; final validation; preparing physics; preparing graphics; publishing; then ready. Cancellation changes the label to “Cancelling…” while admitted work drains. Errors show a concise reason and bounded details. Represent these as a small enum/state record; do not use strings as state-machine keys. Keep phase transitions and terminal outcomes tied to job identity so late results cannot overwrite a newer modal or candidate.

Use the existing ImGui/UI path for one centred modal with a stage label, progress bar, completed/total work when known, and Cancel. Label the bar as **current-stage progress**, with stage ordinal/count, rather than pretending a completed-chunk ratio estimates total elapsed time. For a known total, report actual completed bounded units (chunks, files, templates, upload batches); the denominator is stable for that stage and completion is monotonic. Use an indeterminate bar while a total is genuinely unknown or a dependency is pending, with a truthful label. No timer-driven fake percentages or invented ETA. Do not report overall success at CPU generation completion: keep the modal through physics/GPU preparation and publication, until the first accepted frame for the new world has been presented. A normal finite API or driver call is not a promise of hard real-time execution; measure visible responsiveness and disclose any unresolved stall.

Progress must not block either lane or allocate per cell. Use a fixed per-job phase table with immutable published phase metadata and atomic completed-unit counters; publish phase selection with release/acquire ordering, only after metadata is initialized. The UI reads a coherent selected phase, at most once per update; reading the previous phase during a transition is acceptable, torn fields are not. Workers increment at bounded work-unit completion, not for every sample. No UI calls from workers, no shared mutable label string, no unbounded progress queue, and no lock held by generation that the UI waits on. Terminal completion/error is retained in the owned result and cannot be dropped like a progress notification. UI timing/throttling uses the existing explicit clock.

**Responsiveness through preparation:** send owned, bounded GPU preparation batches to the existing render lane, interleaved with modal frames. Poll upload/fence readiness rather than making the UI wait. Keep world-independent terrain programs/pipeline variants warm from renderer bootstrap; no terrain-content edit recompiles shaders. Preserve existing device/Slang affinity rather than moving their calls to arbitrary workers. Large texture decoding belongs on workers; GPU uploads, creation and retirement belong on their established owner lane, with per-batch work/byte caps and measured timings. Do not pack the entire world into one long render-lane command, exhaust the frame-credit path, or rely on an animated mouse cursor as proof that the modal is repainting. If a required owner-lane operation monopolizes rendering, split/defer it or fix the narrow blocking seam before claiming this requirement complete.

On regeneration, keep the old world rendered behind the modal and pause its simulation/tools; remember its prior pause state. Clear held movement/tool gestures on entry. On failure or cancellation, keep the old session/descriptor intact, restore its prior pause state and leave input neutral. Initial-generation failure or cancellation leaves the no-world UI with Retry and Quit, not an invalid session or automatic process termination. GPU/device failure that makes rendering impossible still follows the existing fatal-device path and preserves diagnostics. Permit cancellation until the update-boundary publication point; a cancel observed before that point wins. After publication, complete the new-world transition rather than pretending it was rolled back.

Cancel only the job's context, not the shared background scheduler. Stop admission, let admitted tasks observe cancellation, settle their group, clean the unpublished CPU candidate on the coordinator, and retire any GPU preparation on the render lane. Keep “Cancelling…” observable until cleanup is settled. Do not destroy a promise/result/job owner while workers still borrow it. Retire an old large grid/catalog/driver off the UI thread after detaching callbacks and proving exclusive ownership; the update-boundary commit is a small owning-pointer/state swap, not a full-world copy or destructor. Keep at most the active world and one candidate/retiring world alive, consistent with the GPU bundle bound.

For ordinary application close during a job, route the close intent into a nonblocking closing/cancellation phase while the UI/render infrastructure is still available. The current run loop exits when `requestExit` is latched: defer that final latch until the job's admitted work and ownership transfers are quiescent. Add only the necessary pre-exit deferral hook in the existing application/window-close control path if no suitable hook exists; do not try to undo a latched exit. Continue pumping native events and progress/closing UI, then invoke the normal exit path and renderer/window/service teardown in dependency order. Do not force-kill workers, run a nested event loop or synchronously join an active generation job from a window-close callback. Fatal-device/process failure retains its established best-effort cleanup path. Final joins after workers are quiescent remain lifecycle cleanup, not a substitute for responsive cancellation.

## Static surface and bindless GPU rendering

Extend `GridPass` and its shader/assets; do not create a parallel terrain renderer or route one triangle mesh per cell through `TrianglePass`. The CPU owns authoritative generation, validation and dirty chunk publication. The GPU owns visibility, indirect draw arguments, contour evaluation, texture coordinates and terrain shading. CPU collider reconstruction on edited chunks is separate from rendering and does not authorize CPU render meshing.

**One surface definition.** Treat static occupancy as binary samples at fine-cell centres. Use the standard 16 marching-squares cases on the dual lattice between four neighbouring centres, with linear edge crossings at midpoints. Fix the bit order as lower-left, lower-right, upper-right, upper-left. Cases 5 and 10 keep the diagonal solid components disconnected; never let chunk order, material ID or camera position choose the saddle. Empty-space connectivity follows the resulting polygons. Use piecewise-linear segments, not bilinear curved fragment boundaries with straight colliders.

Put the small, pure numeric case description in `engine.math` (declarations in its interface, definitions in its matching implementation), with edge endpoints and filled-region triangles. It has current consumers in physics, game validation/volume measurement and rendering, so this sharing is required rather than speculative. Upload this same constant table for shader use; do not hand-maintain a second Slang case table or build a general code generator. Evaluate coverage in the fragment shader from the case's filled triangles. CPU collider extraction uses its boundary segments, oriented with solid on the existing required side. Antialias only the visible edge; the collision surface is the zero-width geometric boundary.

Use this one contour rule for static terrain, including masonry in this milestone. A placed one-metre tile occupies exactly 3 by 3 fine samples and spans a nominal metre, with the shared contour's chamfered exterior corners. Adjacent occupied tiles share a continuous surface. Do not add a second constructed-shape system or claim pixel-square exterior corners. Brick pattern repetition stays one metre even though collision samples are finer. At solid-to-solid interfaces, coverage is the union of occupancy; select the nearest occupied sample in the same filled case component, with global row-major coordinate ties, to choose a categorical material. Never independently alpha-blend each material's silhouette, which would create cracks or double coverage. Internal material interfaces are a texture/material change, not separate colliders.

Keep sample addressing global. Each rendered chunk draws only its own nominal rectangle and reads neighbouring occupancy/material samples through the resident atlas, including diagonal neighbours. No duplicate overlapping halo draws. Outside-world samples follow the protected-solid boundary rule without out-of-bounds reads. Each CPU contour segment has one canonical dual-cell owner; chain stitching/ghost vertices may read adjacent chunks. Preserve chain orientation, hole handling, seam continuity and collider rebuild budgets, with explicit metre conversion. A changed cell can change adjacent dual cells across an edge or corner: invalidate the full affected one-cell neighbourhood in both render publication and collider preparation. Load/prepare required neighbours before drawing or simulating the affected region.

**Material and texture resources.** Reuse the current image pipeline and `BindlessTextureCache` for terrain albedo images, one shared sampler and the descriptor-handle buffer convention from `mesh_bindless.slang`. A small terrain visual record indexed by validated material ID holds tint, resident texture slot and texture period. Its unlit 2D fields differ from the existing 80-byte PBR `GpuMaterial`; this is a concrete reason for a narrow pass-owned record, not for a second texture cache or registry. Material authoring names never enter shaders. Follow current Slang descriptor-handle/nonuniform rules from the shader skill and verified source, not obsolete codemap annotations. Declare and test exact CPU/Slang size, alignment, offsets and bounds.

The GPU receives persistent terrain material IDs, which define geometry. Inspection modes may additionally upload a u16 presentation-index atlas and an RGBA palette; they must not overwrite the terrain-ID atlas or make palette indices into occupancy. Allocate that auxiliary atlas only when needed, reuse its storage across mode changes, and release it with its owning resource bundle. A dense u16-indexed palette is bounded at 1 MiB; one packed full-world u16 cell version is 32 MiB. The bounded spare chunk slots described below permit up to 64 MiB per atlas. Account for the extra diagnostic atlas, textures, slot resources and concurrent old/candidate bundles. No full-world UV, vertex, normal or per-frame colour raster is necessary.

**GPU-driven submission.** The normal terrain path has a pass-owned resident chunk table of at most 1024 entries. CPU updates this table and the terrain atlas on publication/edits, not by recreating a visible list every frame. Upload all resident renderable chunk data needed for GPU culling; do not retain the current CPU-visible-only publication assumption. Derive a chunk's visibility bounds in metres from the numeric grid transform. Per frame:

1. Select a completion-safe frame slot; upload the immutable camera-derived frustum/transform constants already owned by the pass.
2. Record a small compute reset of one indirect command to `{vertexCount=6, instanceCount=0, startVertex=0, startInstance=0}`. End it with the required write dependency before culling.
3. Dispatch bounded compute over the resident chunk table. Visible chunks append their IDs into a slot-owned list and increment that command's instance count. Capacity is the admitted table size, so one append per entry cannot overflow. Include the existing conservative edge-touching visibility rule in metre units. Zero visibility leaves zero instances.
4. Transition/barrier compute outputs for shader reads and indirect arguments. Issue **one instanced indirect draw**, with six procedural vertices per visible chunk and zero instance base. The vertex shader reads `visible_chunk_ids[SV_InstanceID]`; do not rely on the existing unproven multi-draw `startInstanceLocation` behaviour. The fragment shader reads terrain IDs, computes the shared contour, derives world UV, and samples the bindless material texture.

Do not read back visibility/counts, CPU-filter the live draw list, map GPU-written indirect arguments, or issue one draw/descriptor binding per material/chunk on this path. Retain a small CPU reference for tests and existing explicitly selected debug fixtures; it is not the default terrain path. No mesh shaders, per-cell instance list, occlusion hierarchy, async-compute queue or general GPU allocator is required.

`DrawContext` currently begins too late for compute. Add an optional preparation callback on the existing draw-submission boundary, with a content-free context exposing the command encoder/device and existing completion governance. Run all such preparation before opening that surface's render pass, on its existing graphics queue/command stream. `GridPass` owns and encodes the reset/cull compute pipelines; `Renderer` only sequences callbacks. Keep cameras and content out of renderer boundary types. Define no-work, failure, abandoned-frame and successful-submit behaviour: failed preparation encodes no dependent draw, publishes no successful terrain acknowledgment, and does not stamp an unsubmitted fence as last use. Follow the existing submit-settlement/finalizer mechanism rather than adding an independent queue/fence protocol.

Extend existing completion-governed ring slots to the visible list and GPU-writable indirect buffer; use device memory with the required UAV/SRV/indirect usage. Never overwrite a slot still in flight. Replace the existing global-idle atlas-write path for interactive terrain with bounded versioned chunk slots: at most 2048 slots per atlas, comprising up to 1024 current chunk versions and 1024 spare/retiring versions. Upload changed chunks into slots absent from all in-flight references, publish their slot indices through the completion-safe frame chunk table, and recycle old slots only after their last submitted use. This is a small pass-local extension of the current chunk cache and retirement machinery, not a general allocator. Publish all chunks in one accepted edit cohort coherently, including required neighbours, so a frame cannot combine half an edit at a seam.

If spare slots or an upload batch budget are exhausted, retain/coalesce the latest unacknowledged CPU chunk revision and defer publication; continue drawing the previous accepted terrain and UI. Do not overwrite busy slots, lose edit obligations or wait for global GPU idle. Keep rendered/collider revisions coherent before accepting movement through edited geometry; defer the edit's gameplay publication if necessary. Initial/candidate atlases have no prior readers and upload incrementally while the loading UI renders from independent resources. Apply the same lifetime protection to diagnostic atlas updates. Record bounds, deferred work and uploaded bytes. Clean camera motion must not trigger atlas writes, CPU meshing, global GPU waits or full-world uploads. Retire textures, descriptors, buffers, roots and pipelines only after their last submitted use. Device-loss and partial setup paths follow the established pass lifecycle and explicit error contracts.

Texture images are part of the content pack and its fingerprint, with bounds on decoded size/count and verified paths. Supply original, modest repeating material textures to demonstrate coherent surfaces across cells and chunks. A diagnostic flat colour mode remains useful; it does not satisfy the default textured-rendering requirement. CPU-only preview exports can remain flat diagnostic maps and must say so; use actual GPU captures for surface/texture acceptance.

Add `--worldgen-preview` for generation plus diagnostic exports without running the game. Verify a data-only edit from the deployed executable working directory.

Catalog loading, generation and candidate runtime preparation run through the asynchronous job before replacing the live session. Temperature renders only terrain cells with a defined temperature. Biome mode may cover empty terrain to show region ownership; initial-matter mode colors only initialized empty polygon areas at/below the saved fill height. Reject unknown material IDs before deriving either payload. Create/upload palettes on content or preview changes rather than rebuilding them each frame. Carry this revision through owned requests and acknowledgments so an older in-flight mode cannot overwrite or acknowledge the new one. Validate CPU/Slang layouts and bounds. Do not add game imports or a material registry to `Renderer`.

All paths that inspect, paint, dig, build or prepare colliders must respect material representation and diggability. Resolve a named default wall material once from the profile. The physics adapter sends 0/1 occupancy and explicit metric transform for static collidable terrain; it never passes particle initialization IDs as solids. Validate the entire 3 by 3 tile footprint before accepting placement, including avatar overlap and all touched chunks. Existing progressive construction may complete in fine-cell work units, but its reservation/footprint remains a one-metre tile. Extend the existing panel with a compact World generation section: pack/profile/seed, generator/content identity, reload/regenerate, bounded diagnostics and generation timings. ## Implementation sequence

Complete these stages in order; each is a reviewable change set, not an excuse to stop with stubs.

## Acceptance criteria

Use behavior-oriented tests under the correct ownership boundary. Game content/control tests belong in `game.tests`; generic generator tests belong in `engine.tests.sim`; pure math and physics tests cover the shared contour/collider contract; codec tests remain in core only if core changed. App/asset tests cover bindless resources, GPU execution, palette/render transport and lifecycle. Do not import game schemas upward into engine tests.

Required automated evidence:

- Asynchronous startup: no pack/generator/world-physics work before the first successful loading-screen presentation. No-world update/render/inspection paths are valid; minimized startup stays cancellable. With a worker held at a deterministic test gate, native input, modal frames and Cancel continue to be serviced. Test both startup and regenerate without timing-sensitive sleep assertions.
- Progress/lifecycle: stage counters are coherent and monotonic within their stage, unknown totals are labelled indeterminate, final CPU completion is not UI success, and the modal remains until a matching new-world frame is presented. Inject slow I/O, queue saturation, slow chunks and deferred GPU preparation; terminal outcomes are never lost and stale job/progress/upload acknowledgments cannot commit. Cancel before admission, mid-raster, during flood fill/physics/upload, and immediately before publication; preserve the old world and reset input. Initial failure/cancel supports Retry/Quit. Close during each phase drains without use-after-free, UI waits or abandoned channel reservations.
- Parallelism: verify actual concurrent independent chunk execution when multiple workers are available, while one-worker and serial cases remain live. No same-pool parent/child wait deadlock, UI caller fallback, per-cell progress contention or unbounded task queue. Identical numeric results across these modes remain required.
- Catalog: missing files/fields, duplicate key/ID, unknown enum/key/reference, forbidden representation/phase, NaN/infinity, invalid ranges/weights, escaping paths, unsupported versions, excessive counts and deterministic diagnostics. Failed reload does not change the previous catalog/session.
- Data-only extension: add a fixture material with a nonlegacy ID and its own texture, use it in a new biome/deposit, stage only data/assets, then verify generation, inspector name, texture/period/color, diggability and collider occupancy. No C++/shader edits for the extra content. Include noncontiguous IDs and IDs above eight. Missing/corrupt textures and descriptor/decode budget exhaustion fail explicitly.
- Generation: same build/descriptor produces exactly equal terrain, metadata and initial-matter spans under serial and parallel execution, reversed chunk order and reordered TOML records/files. Different seeds produce different outputs. An unused material addition does not perturb RNG streams for existing rules; the content fingerprint still changes.
- Geometry: chunk seams, world edges, protected boundary, nearest-region tie rules, required biome presence, finite temperatures, valid IDs, non-overlapping initial fills, fill containment and mass accounting. Test impossible placement, excessive scratch/output and cancellation without partial publication.
- Scale: fine-cell centres and half-open conversions, negative/out-of-range rejection, three fine cells per metre, nine per one-metre tile, cross-chunk construction where 128 is not divisible by three, final world remainder, metre-based camera/picking/body/collider agreement, and old-scale checkpoint rejection. Verify nine full empty fine cells at unit thickness yield one cubic metre and contour-clipped cells contribute only their empty polygon area.
- Surface: all 16 binary cases including both saddles, isolated samples, cavities, holes, flat support and diagonal boundaries. Compare CPU segments/filled areas with GPU coverage and collision probes. Test seams at four-chunk corners, edits on chunk edges, multiple materials without cracks, texture continuity and metre-period repetition. A saved render capture must show the same walkable surface the body contacts.
- GPU execution: offscreen/edge-touching/empty/all-visible cases produce the correct indirect instance count and chunk coverage in readback tests. Normal frames use GPU visibility and argument writes, zero instance base and one indirect terrain draw. Prove no CPU visibility readback/per-material draws and no clean-frame atlas uploads or global waits using existing counters plus only necessary focused instrumentation. Validate compute-to-draw resource transitions, slot reuse, abandoned frames, device loss and teardown. Compile supported shader targets and run available backend readbacks; disclose unrun backend gates.
- Upload responsiveness: dirty edits and loading never use a global-idle atlas write. Exhaust spare chunk slots deliberately and verify deferred/coalesced publication, retained acknowledgments, safe retirement, coherent edit cohorts/colliders, and continued modal/UI presentation. No hidden full-world copy or old-world destructor runs during the UI commit. Measure preparation batches against the existing frame-cadence configuration and record any missed-frame stalls.
- Control/AI: one normal controlled dupe, reproducible fixed-tick commands, neutral/focus/UI/pause/reload clearing, stable body handles while reversing direction, gravity while walking, and ladder enter/exit without stale control state. An explicit autonomous second agent still plans, advances its path and issues movement. Preserve existing budget/cancellation/partial-path behaviour; do not make human control depend on a GOAP plan.
- Start: every shipped-profile seed in the corpus has the specified supported spawn, clearance, supported resource routes and configured adjacent resource minima after all passes. Do not use the existing point-cell BFS as proof of actor-footprint reachability.
- Transactions: parse/generation/physics/GPU-preparation failure preserves the old world; replacement invalidates old frame acknowledgments; old render work cannot read freed palettes/catalogs/textures; repeated reload and shutdown release resources, including bindless high-water capacity through bundle retirement. Rapid reloads stay within the declared in-flight bundle bound.
- Checkpoints: full capture after clearing dirt still contains the full terrain; save/load preserves IDs, temperatures, descriptor and metadata. A gated worker capture keeps grid/ECS/bodies at one tick, defers dirty acknowledgments, preserves UI presentation, and restores the prior pause/input state on success/failure/cancel. An edited-world round trip preserves the edits and invalidated matter-preview state even after a reservoir wall or original start route is removed. Corrupt/truncated/oversized payloads and wrong pack/version fail before mutation. Do not promise resumed Box2D solver-cache equality beyond the existing replay contract.
- Preview modes: two cells of the same material can show distinct biome/temperature colors without changing terrain IDs or contour coverage; switching modes/ranges refreshes presentation without dirtying simulation, and rejects stale mode payloads/acknowledgments. Biome overlays may intentionally cover empty cells; initial-matter overlay remains clipped to empty geometry.
- Particle boundary: gas, liquid, sand, snow and pebble IDs never occur in terrain payloads or static collider input. Their initialization spans are visible and labelled unsimulated. Editing terrain invalidates the baseline-matter preview instead of pretending matter moved.

Use targeted small-region tests for the algorithms and a bounded full-world corpus for integration. Start with full-world seeds 0, 1, 42 and the maximum u64 seed for each shipped profile; add any failure seed permanently. Expand the corpus only when a failure or unresolved concern justifies it. The full seed range must survive CLI/descriptor parsing even though TOML's integer domain is signed 64-bit; retain the existing CLI behavior and use a canonical hexadecimal string for seed values in any text recipe export.

Inspect exported overviews and closeups for those seeds: coherent material masses, varied cave shapes, visible biome differentiation, deposits with usable scale, no chunk seams, no clipped templates, no excessive isolated speckles and a readable start. Keep images and reports in the normal untracked output tree and summarize any tuning changes. Automated counts alone do not establish useful terrain.

Inspect actual GPU-rendered closeups and an interactive single-dupe traversal in addition to diagnostic maps. Measure a stationary camera, camera pan/zoom, seam edit, preview switch and regeneration on recorded hardware/build/backend. Report CPU submission cost, GPU terrain cost where existing timestamps support it, draw/dispatch counts, uploaded bytes, atlas waits, texture/descriptor usage and peak CPU/GPU memory. Include active-plus-candidate cost and repeated reload behaviour. Do not invent commercial frame budgets or assert scalability from indirect draw counts alone; unresolved stalls, leaks, invalid geometry or missing validation remain explicit limitations.

Record startup-to-first-loading-frame and loading-frame-to-ready-world times separately. During full-world generation, decoding, physics preparation, GPU upload, cancellation and old-world disposal, record maximum observed UI update/presentation gaps, native input/Cancel latency, worker utilization and queue depth on the same hardware/build. Compare with the existing configured frame cadence; asynchronous dispatch by itself does not prove a responsive UI. Capture the actual progress modal at several phases. Treat a reproducible long UI/modal stall caused by this pipeline as a failed acceptance condition, not a permitted loading-screen exception.

Follow the actual `build-system` Windows procedure: persistent VS 18 Insiders vcvars shell, current presets/targets and one matrix invocation at a time. Run formatting Fix/Check and touched-file semantic style checks, current IDE inspection procedure where available, and reviewer validation. This work touches shared configuration consumers, app presentation and render transactions, so phase completion requires the full twelve-entry CTest matrix including asset and both shipped-profile validators, plus three-loop affected suites for the lifetime/transaction changes. Restore `PPR_TEST_LOOPS=1` afterward. Run the prescribed platform/build configurations; explicitly disclose any unavailable gate. Do not use retired time-trial/profile commands from historical designs.

Report implemented behavior, authoring/run commands, validation results, seed/image/report locations, measured generation/render costs, UI responsiveness and memory, and exact remaining limitations. Completion means the window/render loop and progress modal appear before asynchronous generation starts; normal startup/reload/cancel remain responsive; the application uses the data pack at the 3:1 scale, shows textured contours through the bindless GPU-driven path, starts one directly controlled dupe while preserving AI, supports the second profile and material-extension demonstration, and passes the required failure/ownership tests.
